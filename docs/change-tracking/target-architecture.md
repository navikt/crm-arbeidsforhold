# Target architecture

## Design goals

1. Keep the solution small and AAREG-specific.
2. Track only meaningful business activity initiated by crm-arbeidsforhold.
3. Avoid a generic org-wide audit framework.
4. Make it easy to query and review from reports and support flows.
5. Keep operational logging separate from business activity tracking.

## Recommended implementation

Create one custom object for AAREG activity tracking, for example:

- AAREG_Activity_Log__c

This is the central record used to store concise activity entries generated by the app.

## Core concept

Each record in the activity log represents one business event, for example:

- ApplicationCreated
- ApplicationSubmitted
- AgreementUpdated
- DecisionCreated
- AccessRequestUpdated
- InquiryCreated
- AttachmentLinked
- StatusChanged

## Essential fields

- Application__c
- RelatedRecordId__c
- RelatedObjectApiName__c
- ActivityType__c
- ActivitySummary__c
- CorrelationId__c
- SourceClass__c
- SourceMethod__c
- UserId__c
- PayloadJson__c

## Logging pattern

The app should call one shared helper such as:

- AAREG_ActivityService.logActivity(...)

This helper should insert a single activity record after meaningful domain actions complete successfully.

## Operational logging remains separate

The existing technical logging framework should still be used for:

- integration failures,
- retries,
- API exceptions,
- callout diagnostics,
- lower-level service errors.

The custom activity object is for business activity visibility, not for system debugging or exception logging.

## Constraints

- Do not log every DML operation.
- Do not capture secrets, tokens, or unnecessary personal data.
- Do not rely on user identity alone to identify application ownership.
- Keep the object focused on business intent and workflow traceability.
